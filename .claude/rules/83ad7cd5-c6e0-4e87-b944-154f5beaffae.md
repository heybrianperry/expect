<rule_activation id="83ad7cd5-c6e0-4e87-b944-154f5beaffae" title="Adopt Browser-Based Rendering Model with Session Replay Capabilities" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the project.

**Context**: The codebase implements browser-based rendering with DOM manipulation and event recording capabilities to capture user sessions and replay them accurately for debugging, testing, and demonstration purposes.

**In scope**:
- All browser-based frontend rendering components
- Session recording and replay infrastructure
- Demo recording scripts and automation tools
- Element locator resolution and identification systems
- Video generation from recorded sessions

**Out of scope**:
- Server-side rendering (SSR) implementations
- Native mobile application rendering
- Backend API response rendering
- Static site generation processes
- Third-party embedded widgets with isolated rendering contexts

**Exceptions**:
- EXC-001: Performance-critical components require server-side rendering for initial page load optimization
- EXC-002: Third-party integrations do not support DOM-based event capture
</rule_activation>

### Rules

- **R-BRR-001** MUST: All frontend rendering MUST be performed in a browser environment with full DOM access to enable accurate event capture and replay.

- **R-BRR-002** MUST: Session replay components MUST capture sufficient state information to reconstruct user interactions with high fidelity.

- **R-BRR-003** MUST: Locator resolution utilities MUST provide consistent element identification across live and replay contexts.

- **R-BRR-004** SHOULD: Recording and replay functionality SHOULD be implemented as separate, composable modules to support different use cases (debugging, demos, testing).

- **R-BRR-005** SHOULD: The rendering model SHOULD support video output generation from recorded sessions for documentation and demonstration purposes.

- **R-BRR-006** MAY: Implementations MAY optimize replay performance by pre-processing recorded events or using virtual DOM techniques.

### Implementation Notes

- Use the rrvideo.ts module for video generation from recorded sessions, ensuring consistent output format across different recording scenarios
- Leverage resolve-locator.ts utilities for all element identification to maintain consistency between live interaction and replay contexts
- Implement record-demo.ts scripts as part of CI/CD pipeline to automatically generate demonstration videos for new features
- Consider using data attributes (data-testid, data-replay-id) on critical UI elements to ensure stable locator resolution across DOM changes
- Establish clear guidelines for what data should be excluded from recording (password fields, payment information, etc.) and implement automatic sanitization

**Accept when:**
- All three key modules (rrvideo, resolve-locator, record-demo) are present and actively used in the codebase
- Session replay functionality successfully reconstructs user interactions with >95% fidelity
- Locator resolution utilities are consistently used across all component tests and replay scenarios
- Performance overhead of recording infrastructure is <5% impact on key user interaction metrics

<enforcement>
Claude Code MUST verify compliance with these rules when:
- Implementing or modifying frontend rendering components
- Adding session recording or replay functionality
- Creating demo recording scripts
- Implementing element locators or identifiers
- Generating video output from sessions

Violation handling:
- Pull requests introducing alternative rendering models without architectural approval are blocked
- Code using non-standard locator resolution approaches triggers review warnings
- Performance regressions exceeding 5% overhead require optimization or feature flag implementation
- Privacy violations in recorded data trigger immediate incident response and recording suspension

Exception process:
- Submit exception request to Frontend Architecture Team with justification and impact analysis
- For performance-critical paths, provide benchmarks demonstrating necessity of exception
- Document approved exceptions in architecture decision log with expiration date for review
- Exceptions require quarterly review to assess if they can be brought into compliance
</enforcement>
