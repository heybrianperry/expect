<rule_activation id="481736c1-b05e-482c-859c-5d94d5cae50f" title="Standardize React Hooks for UI State Management in CLI Components: Components Use Additional" applies_to="apps/cli/src/**/*.{ts,tsx}">
These rules are ALWAYS ACTIVE for all React-based CLI components and hooks in `apps/cli/src/`.

**In scope:**
- All React-based CLI screen components in apps/cli/src/components/screens/
- Custom hooks in apps/cli/src/hooks/
- Interactive terminal UI components requiring state management
- Components handling user input, async operations, or multi-step workflows

**Out of scope:**
- Non-React CLI utilities and pure functions
- Backend services or API handlers
- Static configuration files
- Build scripts and tooling configuration

**Exceptions:**
- EXC-001: Integrating with third-party libraries that require class components or legacy patterns
</rule_activation>

### Rules

- **R-RH-001** MAY: Components MAY use additional React hooks from the ecosystem (useMemo, useRef, useContext) when performance optimization or context access is required
- **R-RH-002** MUST: No class-based components in apps/cli/src/components/screens/ directory (screen components must use functional components with hooks)
- **R-RH-003** MUST: All custom hooks in apps/cli/src/hooks/ MUST follow the 'use-*.ts' or 'use-*.tsx' naming convention
- **R-RH-004** MUST: Screen components MUST demonstrate usage of React hooks (useState, useEffect, useCallback) for state management
- **R-RH-005** MUST: ESLint configuration MUST include react-hooks plugin with recommended rules enabled
- **R-RH-006** SHOULD: Custom hooks SHOULD be placed in apps/cli/src/hooks/ directory
- **R-RH-007** SHOULD: Custom hooks SHOULD be documented with JSDoc comments explaining parameters, return values, and usage examples
- **R-RH-008** SHOULD: Extract custom hooks only when reused in 2+ places, or complex logic >50 lines to avoid over-abstraction

### Verify

```bash
# Verify no class-based components in screen components
grep -r 'class.*extends.*Component' apps/cli/src/components/screens/ | wc -l | grep -q '^0$'

# Verify custom hooks follow naming convention
find apps/cli/src/hooks -name 'use-*.ts' -o -name 'use-*.tsx' | wc -l

# Verify screen components use React hooks
grep -r 'useState\|useEffect\|useCallback' apps/cli/src/components/screens/*.tsx | wc -l
```

**Accept when:**
- No class-based components exist in apps/cli/src/components/screens/ directory
- All custom hooks in apps/cli/src/hooks/ follow the 'use-*' naming convention
- Screen components demonstrate usage of React hooks (useState, useEffect, useCallback) for state management
- ESLint configuration includes react-hooks plugin with recommended rules enabled

<enforcement>
Claude Code MUST NOT skip or defer verification. All verification commands must be executed and pass before considering the implementation complete.

**Enforcement mechanisms:**
- ESLint checks in CI pipeline with react-hooks plugin enabled
- Code review checklist includes verification of hook usage patterns
- Automated grep-based checks in pre-commit hooks to detect class components in screen directories

**Violation handling:**
- CI build fails if ESLint detects hook rule violations
- PR reviews must address any class components introduced in screen directories
- Tech lead review required for any exceptions to the hooks-first approach

**Exception process:**
1. Document the technical constraint requiring an exception in the PR description
2. Obtain approval from tech lead or architecture review board
3. Add inline comments explaining the exception and any planned migration path
4. Track exceptions in technical debt backlog for future resolution
</enforcement>
