<rule_activation id="d346c8d7-3981-4bfa-aa81-2f3d67bba76c" title="Standardize Custom Error Classes for External API Error Handling" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in packages exposing public/external APIs, CLI applications with external-facing commands, SDK modules, and API endpoints that cross package boundaries.

**In scope:**
- All packages exposing public/external APIs (packages/cookies, packages/browser, etc.)
- CLI applications with external-facing commands and utilities (apps/cli)
- SDK modules and libraries intended for third-party consumption
- API endpoints and integration points that cross package boundaries

**Out of scope:**
- Internal utility functions not exposed in public API surfaces
- Private implementation details within a single module
- Test utilities and mock implementations
- Temporary or experimental features not yet stabilized for external use
</rule_activation>

### Rules

- **R-ERR-001** MUST: All public/external API modules MUST define custom error classes that extend the base Error class for domain-specific error conditions.
- **R-ERR-002** MUST: Custom error classes MUST be exported from dedicated error modules (e.g., errors.ts) to ensure they are accessible to API consumers.
- **R-ERR-003** MUST: Custom error classes MUST set the error name property to a descriptive, unique identifier that clearly indicates the error type.
- **R-ERR-004** SHOULD: Custom error classes SHOULD include additional context properties beyond the standard message field (e.g., error codes, validation details, HTTP status codes).
- **R-ERR-005** SHOULD: Error modules SHOULD be co-located with the API implementation in the same package to maintain cohesion.
- **R-ERR-006** MUST: Public API functions MUST throw custom error instances rather than generic Error objects or string literals.
- **R-ERR-007** MAY: Custom error classes MAY implement additional methods for error serialization, logging, or transformation to support observability requirements.

### Verify

```bash
# Check for custom error classes in packages and apps
grep -r "class.*Error extends Error" packages/*/src/errors.ts apps/*/src/**/errors.ts

# Verify error classes are exported
grep -r "export class.*Error" packages/*/src/errors.ts apps/*/src/**/errors.ts

# Find all errors.ts files and check they extend Error
find packages apps -name 'errors.ts' -type f | xargs grep -l "extends Error"
```

**Accept when:**
- All public/external API packages contain an errors.ts module that exports at least one custom error class
- Custom error classes properly extend Error and set the name property to a descriptive identifier
- Public API functions throw custom error instances rather than generic Error objects in documented error conditions

### Implementation Notes

- Create a base custom error class that extends Error and properly sets the prototype chain for instanceof checks to work correctly across different JavaScript environments
- Use TypeScript's class syntax with proper type annotations for error properties to enable type checking in consumer code
- Export all custom error classes from a dedicated errors.ts module at the package root or alongside the main API entry point
- Include JSDoc comments on error classes documenting when they are thrown and what properties they contain
- Consider creating error factory functions for complex error construction scenarios to encapsulate error creation logic

Claude Code MUST NOT skip or defer verification. Automated code review checks using AST analysis MUST detect throw statements with generic Error objects in public API modules. Manual code review during pull request approval MUST focus on error handling patterns in new or modified public APIs. Pull requests introducing new public APIs without custom error classes MUST be flagged for revision.
</enforcement>
