<rule_activation id="c46593d9-c90f-4499-b0f9-d93531744989" title="Standardize Environment Variable Access Through Centralized Configuration Constants: Environment Variables Read" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files to ensure environment variables are accessed through centralized configuration.

**In scope:**
- All CLI application modules requiring configuration values
- Build tool configuration files (vite.config.ts, webpack.config.js, etc.)
- Runtime utilities and services that depend on environment-specific behavior
- Test fixtures and mocks that need to override configuration values

**Out of scope:**
- Third-party libraries that manage their own configuration
- Development-only scripts that explicitly document direct env access
- Infrastructure deployment scripts outside the application codebase

**Exceptions:**
- EXC-001: Build tool configuration files (vite.config.ts) that must access environment variables to configure the build process
- EXC-002: Bootstrap/initialization code that sets up the configuration system itself
</rule_activation>

### Rules

- **R-ENV-001** MUST: Environment variables MUST be read and validated at application initialization time, not lazily throughout execution.
- **R-ENV-002** MUST: All environment variables MUST be accessed through a centralized constants.ts or config.ts module, not directly via process.env or import.meta.env throughout the codebase.
- **R-ENV-003** MUST: Configuration values MUST be exported as typed constants with explicit TypeScript types (e.g., `const API_URL: string = process.env.API_URL || ''`).
- **R-ENV-004** MUST: Required environment variables MUST be validated at module initialization with descriptive errors if missing.
- **R-ENV-005** SHOULD: Provide a .env.example file documenting all required and optional environment variables with descriptions.
- **R-ENV-006** MUST: Configuration module MUST remain as a leaf dependency with no imports from other application code to prevent circular dependencies.

### Verify

```bash
# Check for direct process.env access outside configuration modules
grep -r 'process\.env\.' --include='*.ts' --include='*.js' --exclude='*constants.ts' --exclude='*config.ts' --exclude='vite.config.ts' apps/cli/src/

# Check for direct import.meta.env access outside build configuration
grep -r 'import\.meta\.env\.' --include='*.ts' --exclude='vite.config.ts' apps/cli/src/

# Verify configuration module exists
test -f apps/cli/src/constants.ts && echo 'Configuration module exists' || echo 'Missing constants.ts'
```

**Accept when:**
- No direct process.env or import.meta.env access found in application code outside of designated configuration modules (constants.ts, config.ts, vite.config.ts)
- All configuration values are exported from a centralized constants or config module with explicit types
- Required environment variables are validated at application startup with clear error messages
- Configuration module has no imports from other application modules (leaf dependency)

<enforcement>
Claude Code MUST NOT skip or defer verification. When working with configuration:
- Check for direct environment variable access before accepting changes
- Ensure all new configuration goes through the centralized module
- Validate that types are explicitly declared for all configuration exports
- Confirm that exceptions (EXC-001, EXC-002) are properly documented when applicable
- CI pipeline MUST fail if direct environment access is detected outside approved files
</enforcement>
