<rule_activation id="957d457b-237a-4436-8c00-9d7d02946285" title="Standardize Public API Error Handling and Event Contracts" applies_to="**/*">
These rules are ALWAYS ACTIVE for all public-facing API modules, external integration points, and client-facing SDK components. This applies to error handling, event contracts, and constant definitions exposed to external consumers.
</rule_activation>

### Rules

- **R-APIC-001** MUST: All public-facing API modules MUST define their error contracts in dedicated error definition files (e.g., errors.ts) that export typed error classes or error code constants.
- **R-APIC-002** MUST: Public API constants that form part of the external contract MUST be defined in dedicated constants files (e.g., constants.ts) separate from implementation logic.
- **R-APIC-003** MUST: Event schemas for public APIs MUST be defined in dedicated event definition files (e.g., viewer-events.ts) with explicit type definitions for all event payloads.
- **R-APIC-004** MUST: Error definitions MUST include machine-readable error codes or types that remain stable across versions to enable programmatic error handling by consumers.
- **R-APIC-005** SHOULD: Public API contracts SHOULD be versioned and changes to error codes, constants, or event schemas SHOULD follow semantic versioning principles.
- **R-APIC-006** SHOULD: Contract definition files SHOULD be co-located with their respective package modules (e.g., packages/browser/src/*/errors.ts) to maintain clear ownership.
- **R-APIC-007** MUST_NOT: Public API contract definitions MUST NOT contain implementation logic or business rules; they MUST only define the interface contract.
- **R-APIC-008** MAY: Packages MAY provide utility functions for extracting or transforming contract artifacts (e.g., extract-close-artifacts.ts) as long as the core contracts remain stable.

### Scope

**In scope:**
- All packages exposing public APIs to external consumers (browser SDKs, CLI tools, public npm packages)
- Error handling contracts for cross-package boundaries
- Event schemas for MCP and viewer integrations
- Constant definitions used in public API signatures or responses
- Platform-specific API implementations (iOS, browser) that share common contract patterns

**Out of scope:**
- Internal-only modules and utilities not exposed to external consumers
- Private implementation details within a package
- Development and testing utilities
- Internal event buses or messaging systems not exposed as public APIs

**Exceptions:**
- EXC-001: A package is explicitly marked as internal-only and will never be published or consumed externally
- EXC-002: Rapid prototyping or experimental features marked as alpha/unstable with explicit warnings

### Verify

```bash
# Count contract definition files in packages and apps
find . -path '*/src/*/errors.ts' -o -path '*/src/*/constants.ts' -o -path '*/src/*-events.ts' | grep -E '(packages|apps)' | wc -l

# Check for error exports in errors.ts files
grep -r 'export.*Error' --include='errors.ts' packages/ apps/ | head -5

# Check for constant exports in constants.ts files
grep -r 'export const' --include='constants.ts' packages/ apps/ | head -5
```

**Accept when:**
- Each public-facing package contains at least one contract definition file (errors.ts, constants.ts, or events.ts) in its source tree
- Contract files export only type definitions, interfaces, constants, or error classes without implementation logic
- Error definitions include stable identifiers (error codes or discriminated type fields) that enable programmatic handling
- Contract files are referenced in package documentation or API reference materials

<enforcement>
Claude Code MUST NOT skip or defer verification. Changes to contract files (errors.ts, constants.ts, *-events.ts) in public-facing packages require:
- Automated linting to detect implementation logic in contract files
- Architecture review for contract modifications
- CI pipeline checks for breaking changes using API surface comparison tools
- Explicit version bump and changelog entry for breaking changes
</enforcement>
