<rule_activation id="8c3c25c9-cf13-4bc9-980f-1cef66630d1c" title="Standardize External Client Libraries for Third-Party Service Integration" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files in the codebase.

External service integrations (HTTP/REST APIs, WebDriver, browser automation, remote state management, third-party SaaS platforms, external databases) must follow standardized client library patterns.

**In scope:**
- All integrations with external HTTP/REST APIs
- WebDriver and browser automation service clients
- Remote state management and synchronization services
- Third-party SaaS platform integrations
- External database or storage service clients

**Out of scope:**
- Internal service-to-service communication within the same deployment
- Standard library HTTP utilities for one-off requests
- Native browser APIs or DOM manipulation
- File system or local resource access

**Exceptions:**
- EXC-001: Proof-of-concept or experimental integrations with services not yet approved for production use
- EXC-002: Simple webhook receivers or one-time data import scripts with no ongoing maintenance requirements
</rule_activation>

### Rules

- **R-EXT-001** MUST: External service integrations MUST be encapsulated in dedicated client library modules with clear boundaries.
- **R-EXT-002** MUST: Client libraries MUST provide typed interfaces that abstract the underlying service API details from consuming code.
- **R-EXT-003** MUST: Connection management and authentication logic MUST be centralized within the client library implementation.
- **R-EXT-004** SHOULD: Client libraries SHOULD implement consistent error handling patterns including retry logic and timeout management.
- **R-EXT-005** SHOULD: External client modules SHOULD be placed in dedicated directories or packages that clearly identify them as external integration points.
- **R-EXT-006** SHOULD: Client libraries SHOULD provide configuration options for connection parameters, timeouts, and service endpoints.
- **R-EXT-007** MAY: Client libraries MAY implement caching or connection pooling when appropriate for the service characteristics.

### Verify

```bash
# Check for client class implementations
grep -r "class.*Client" --include="*-client.ts" packages/ apps/

# Count client library files
find . -type f -name "*-client.ts" -o -name "*-client.js" | wc -l

# Detect direct HTTP calls outside client libraries
grep -r "import.*axios\|fetch" --include="*.ts" packages/ apps/ | grep -v "client.ts" | wc -l
```

**Accept when:**
- All external service integrations are encapsulated in dedicated client modules with clear naming conventions
- Client libraries provide typed interfaces and do not expose raw HTTP client details to consumers
- Direct HTTP calls to external services outside of client libraries are limited to exceptional cases with documented justification
- New external service integrations follow the established client library pattern without requiring architectural review

<enforcement>
Claude Code MUST verify compliance with external client library patterns when:
- Creating new external service integrations
- Modifying existing client libraries
- Adding direct HTTP calls to external services

Verification MUST NOT be skipped or deferred.
</enforcement>
