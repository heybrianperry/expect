<rule_activation id="fdabd8ad-5628-425e-97f3-32022ce11eff" title="Establish Service Definition Boundaries for Browser Automation Modules" applies_to="packages/browser/src/**/*">
These rules are ALWAYS ACTIVE for all files matching `packages/browser/src/**/*`.

Browser automation modules must maintain clear service boundaries between platform-specific client implementations, runtime evaluation utilities, and DOM element resolution logic to enable testing, maintainability, and platform portability.
</rule_activation>

### Rules

- **R-SB-001** MUST: Browser automation modules MUST separate platform-specific client implementations from cross-platform utility functions.
- **R-SB-002** MUST: Runtime evaluation utilities MUST be isolated in dedicated modules that do not depend on specific WebDriver client implementations.
- **R-SB-003** MUST: DOM element resolution logic MUST be encapsulated in separate utility modules with well-defined input/output contracts.
- **R-SB-004** SHOULD: Service modules SHOULD expose minimal public APIs that hide internal implementation details.
- **R-SB-005** SHOULD: Utility modules SHOULD be stateless and composable to facilitate reuse across different automation contexts.
- **R-SB-006** MUST_NOT: Platform-specific client implementations MUST NOT be directly imported by cross-platform utility modules.
- **R-SB-007** MAY: Modules MAY use dependency injection patterns to allow runtime selection of platform-specific implementations.

### Implementation Notes

- Use TypeScript's module system to enforce boundaries; avoid exporting internal implementation details
- Place platform-specific clients in dedicated subdirectories (e.g., ios/, android/) separate from utils/
- Utility modules should export pure functions or stateless classes that accept dependencies as parameters
- Consider using barrel exports (index.ts) to control the public API surface of each module
- Document module responsibilities and dependencies in README files or inline comments

### Verify

```bash
grep -r "import.*webdriver-client" packages/browser/src/utils/ && echo 'FAIL: Utils importing platform clients' || echo 'PASS'
npx madge --circular packages/browser/src && echo 'Checking for circular dependencies'
find packages/browser/src -name '*.ts' -exec grep -l 'export.*class.*Client' {} \; | grep -v '/ios/' | grep -v '/android/' && echo 'FAIL: Client classes outside platform dirs' || echo 'PASS'
```

**Accept when:**
- No utility modules in packages/browser/src/utils/ directly import platform-specific client implementations
- Dependency analysis shows no circular dependencies between service modules
- All WebDriver client implementations are contained within platform-specific subdirectories

<enforcement>
Claude Code MUST NOT skip or defer verification.

Violation handling:
- CI pipeline fails if circular dependencies are detected
- Pull requests with boundary violations are blocked until refactored
- Architecture review required for any exceptions to boundary rules

Exception process:
- Submit exception request documenting why boundary violation is necessary (e.g., EXC-001: A utility module requires platform detection to select appropriate implementation strategies)
- Obtain approval from two senior engineers or tech lead
- Document exception in code comments and architecture decision log
- Schedule follow-up review to determine if exception can be eliminated
</enforcement>
