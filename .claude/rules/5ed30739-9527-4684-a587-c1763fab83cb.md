<rule_activation id="5ed30739-9527-4684-a587-c1763fab83cb" title="Standardize Utility Module Exports with Single-Purpose Functions" applies_to="**/*">
These rules are ACTIVE for all library and utility module development across the codebase.

**In scope:**
- All utility functions in apps/cli/src/utils/
- All library modules in packages/*/src/ directories
- Store modules and state management utilities
- Client wrappers and API abstraction layers
- Formatting, parsing, and transformation utilities

**Out of scope:**
- React components and UI elements
- Application entry points and main files
- Configuration files and build scripts
- Test utilities and fixtures (may follow different patterns)
- Third-party library re-exports

**Exceptions:**
- EXC-001: A utility module requires multiple related exports that are always used together (e.g., a parser with its associated types and validators)
- EXC-002: Legacy modules being incrementally refactored
</rule_activation>

### Rules

- **R-UTIL-001** MUST: Utility modules MUST export a single primary function or a cohesive set of related functions serving one specific purpose.
- **R-UTIL-002** MUST: Module file names MUST clearly describe their single responsibility using kebab-case (e.g., format-elapsed-time.ts, copy-to-clipboard.ts).
- **R-UTIL-003** MUST: Public API exports MUST be explicitly defined using named exports; default exports SHOULD be avoided for utility functions.
- **R-UTIL-004** SHOULD: Utility modules SHOULD be organized in a dedicated utils/ or similar directory structure to maintain clear separation from business logic.
- **R-UTIL-005** SHOULD: Each utility module SHOULD have minimal external dependencies to maximize reusability and minimize coupling.
- **R-UTIL-006** MUST_NOT: Utility modules MUST NOT contain side effects at module initialization; all effects must be contained within exported functions.
- **R-UTIL-007** SHOULD: Library modules providing client interfaces (e.g., query-client.ts, webdriver-client.ts) SHOULD export factory functions or class constructors with clear initialization patterns.
- **R-UTIL-008** MAY: Utility modules MAY export TypeScript types and interfaces alongside functions when they form part of the public API contract.

### Implementation Notes

- When creating a new utility, ask: 'Does this do exactly one thing?' If the answer is no, consider splitting into multiple modules
- Use descriptive, verb-based names for utility files that clearly indicate their purpose (e.g., build-image-sequence.ts, clear-ink-display.ts)
- Place utility modules in a utils/ directory at the appropriate package level; avoid deeply nested utility directories
- Export TypeScript types alongside functions when they are part of the public API contract, but keep type definitions focused
- For client libraries (query-client.ts, webdriver-client.ts), prefer factory functions or clear initialization patterns over complex constructors

### Verify

```bash
# Check that utility modules don't use default exports
find apps/cli/src/utils -name '*.ts' -exec sh -c 'grep -L "export default" "$1" || exit 0' _ {} \;

# Count named exports in utility modules
grep -r "export {" apps/cli/src/utils packages/*/src --include="*.ts" | wc -l

# Inspect utility and client module structure
find . -path '*/utils/*.ts' -o -path '*/src/*-client.ts' -o -path '*/src/layers.ts' | xargs -I {} sh -c 'echo "Checking: {}"; head -20 {}'

# Enforce no default exports via ESLint
eslint --rule 'import/no-default-export: error' 'apps/cli/src/utils/**/*.ts' 'packages/*/src/**/*-client.ts'
```

**Accept when:**
- All utility modules in utils/ directories use named exports exclusively (no default exports)
- Each utility module file name clearly describes a single responsibility using kebab-case
- Utility modules contain no side effects at module initialization (verified by static analysis)
- New utility modules pass code review checklist confirming single-purpose design

<enforcement>
Claude Code MUST verify compliance with these rules when creating or modifying utility modules. Verification MUST NOT be skipped or deferred.

**Violation handling:**
- CI pipeline fails if ESLint rules detect default exports in utility modules
- Code review requires changes before approval if modules violate single-purpose principle
- Existing violations are tracked in technical debt backlog with refactoring plans
- Quarterly architecture reviews identify and prioritize cleanup of non-compliant modules

**Exception process:**
- Developer documents exception rationale in module JSDoc comments
- Exception request submitted to tech lead or architecture review board
- Approved exceptions are logged in ADR amendments or architecture decision log
- All exceptions require periodic review (every 6 months) to determine if still necessary
</enforcement>
