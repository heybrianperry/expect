<rule_activation id="dd979afd-ab23-4f95-b147-1071ee252368" title="Adopt Browser-Based Rendering with Locator Resolution for UI Automation: Locator Resolution Support" applies_to="**/*">
These rules are ALWAYS ACTIVE for all browser-based UI automation including testing, demo recording, screenshot generation, element locator resolution, browser lifecycle management, and automated interaction workflows.

Out of scope: Server-side rendering (SSR), static site generation (SSG), client-side framework rendering logic, manual browser testing.
</rule_activation>

### Rules

- **R-BRL-001** SHOULD: Locator resolution SHOULD support multiple locator strategies (CSS selectors, XPath, text content, etc.) to maximize element identification reliability.
- **R-BRL-002** MUST: Browser control logic MUST be placed in packages/browser/src/browser.ts with clear API for launch, navigation, interaction, and cleanup operations.
- **R-BRL-003** MUST: Locator resolution utility MUST be implemented in packages/browser/src/utils/resolve-locator.ts supporting multiple locator strategies with fallback mechanisms.
- **R-BRL-004** SHOULD: Automation scripts (e.g., demo recording) SHOULD be stored in application-specific script directories like apps/website/scripts/ for organizational clarity.
- **R-BRL-005** SHOULD: UI components SHOULD include data-testid or data-automation attributes to provide stable locator targets independent of visual styling changes.
- **R-BRL-006** MUST: New browser automation code MUST use centralized browser control and locator utilities, not inline browser automation logic.
- **R-BRL-007** SHOULD: Locator strategies SHOULD implement multiple fallback methods to handle UI structure changes gracefully.

### Verify

```bash
# Verify browser control and locator utilities exist
find . -path '*/browser/src/browser.ts' -o -path '*/browser/src/utils/resolve-locator.ts' | grep -q . && echo 'Browser control and locator utilities found'

# Check for locator resolution usage
grep -r 'resolve.*locator|locator.*resolve' --include='*.ts' --include='*.js' packages/browser/ 2>/dev/null | wc -l

# Verify demo/recording scripts are in app directories
find apps/*/scripts -name '*demo*.ts' -o -name '*record*.ts' 2>/dev/null | grep -q . && echo 'Demo/recording scripts found in app script directories'
```

**Accept when:**
- Browser control module exists at packages/browser/src/browser.ts with encapsulated browser lifecycle management
- Locator resolution utility exists at packages/browser/src/utils/resolve-locator.ts providing consistent element identification
- Automation scripts (demo recording, testing) are organized in dedicated script directories and utilize the browser control and locator utilities
- New browser automation code uses centralized utilities rather than inline browser logic
- Architecture linting rules enforce import patterns requiring use of browser module for browser interactions

<enforcement>
Claude Code MUST NOT skip or defer verification.

Verification is mandatory through:
- Code review process checking that new browser automation uses centralized utilities
- Architecture linting rules enforcing browser module import patterns
- CI pipeline validation that automation tests and demo scripts execute successfully

Violation handling:
