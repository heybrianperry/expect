<rule_activation id="a8708766-7127-497b-bb0b-508bbb6c747a" title="Standardize Environment Variable Validation and Path Resolution for Runtime Configuration" applies_to="**/*">
This ADR is ACTIVE for all runtime configuration and environment management code across the codebase.

Applies to:
- All environment variable access for runtime configuration
- File system path resolution from environment variables or user input
- Platform-specific configuration directory resolution (HOME, AppData, Library, etc.)
- Configuration validation in CLI tools, browser automation, and utility packages
- Cookie storage path resolution and browser profile path handling

Out of scope:
- Build-time configuration and compile-time constants
- Hard-coded internal paths that are not derived from external input
- Test fixtures and mock configuration in test suites
- Third-party library configuration that is managed by the library itself
</rule_activation>

### Rules

- **R-ENV-001** MUST: All environment variables used for configuration MUST be validated before use, checking for null/undefined values and appropriate data types.
- **R-ENV-002** MUST: File system paths derived from environment variables or user input MUST be normalized and validated to prevent path traversal attacks.
- **R-ENV-003** MUST: Configuration resolution logic MUST provide clear error messages indicating which environment variable or configuration parameter is missing or invalid.
- **R-ENV-004** SHOULD: Platform-specific path resolution (e.g., HOME directory, application data directories) SHOULD use dedicated utility functions rather than inline string concatenation.
- **R-ENV-005** SHOULD: Default values for optional configuration parameters SHOULD be explicitly documented and consistently applied across the codebase.
- **R-ENV-006** MUST_NOT: Configuration code MUST NOT trust user-provided paths without validation and sanitization.
- **R-ENV-007** MAY: Configuration modules MAY cache resolved and validated configuration values to avoid repeated validation overhead.

### Verify

```bash
# Check for unvalidated process.env access
grep -r 'process\.env\.' --include='*.ts' --include='*.js' | grep -v 'validate\|check\|sanitize' | wc -l

# Check for unvalidated path construction from environment variables
grep -r 'path\.join.*process\.env' --include='*.ts' --include='*.js' | grep -v 'path\.normalize\|path\.resolve' | wc -l

# Run configuration validation tests
npm test -- --grep 'configuration.*validation'
```

**Accept when:**
- All direct access to process.env includes validation or uses a validated configuration wrapper
- All file system paths constructed from environment variables or user input are normalized and validated
- Configuration validation tests pass with 100% coverage for all environment variables and path resolution logic

<enforcement>
Claude Code MUST NOT skip or defer verification.

Violation handling:
- Pull requests with unvalidated environment variable access are blocked until validation is added
- Security team is notified of violations in production code for immediate remediation
- Violations are tracked in security audit logs and reviewed quarterly

Exception process (EXC-001):
- Developer submits exception request with justification to tech lead
- Tech lead reviews security implications and approves or rejects with documented reasoning
- Approved exceptions are documented in code comments with expiration date and must be reviewed annually
- Development and testing environments where security validation may be relaxed for debugging purposes
</enforcement>
