<rule_activation id="5d1a45ae-ecb0-4b72-b072-3666a576931f" title="Standardize React Hooks for Component State Management in CLI Screens" applies_to="**/*">
These rules apply to all React-based screen components in the CLI application, custom hooks, and any new CLI screen components or interactive UI elements.
</rule_activation>

### Rules

- **R-HOOKS-001** MUST: All CLI screen components MUST use React hooks (useState, useEffect, useCallback, etc.) for managing component state and side effects rather than class-based component lifecycle methods.
- **R-HOOKS-002** MUST: Complex or reusable state logic MUST be extracted into custom hooks following the 'use-' naming convention (e.g., use-test-coverage).
- **R-HOOKS-003** SHOULD: Custom hooks SHOULD encapsulate a single concern or responsibility to promote reusability and testability.
- **R-HOOKS-004** MUST: Screen components MUST separate presentation logic from business logic, with business logic encapsulated in custom hooks.
- **R-HOOKS-005** SHOULD: Custom hooks that interact with message queues or asynchronous boundaries SHOULD handle cleanup in useEffect return functions to prevent memory leaks.
- **R-HOOKS-006** MAY: Screen components MAY compose multiple custom hooks to build complex functionality from simpler, tested units.
- **R-HOOKS-007** MUST_NOT: Screen components MUST NOT contain direct business logic or data fetching code; these MUST be delegated to custom hooks.

### In Scope

- All React-based screen components in the apps/cli/src/components/screens directory
- Custom hooks in the apps/cli/src/hooks directory
- Any new CLI screen components or interactive UI elements
- State management for user interactions, data fetching, and side effects in CLI screens

### Out of Scope

- Non-React components or pure utility functions
- Backend services or API implementations
- Static configuration files or constants
- Third-party library implementations

### Exceptions

- **EXC-001**: Legacy screen components that are scheduled for deprecation within the next release cycle
- **EXC-002**: Simple presentational components with no state or side effects

### Verify

```bash
# Check for class-based components in screen directory (should be 0 or only documented exceptions)
grep -r 'class.*extends.*Component' apps/cli/src/components/screens/ | wc -l

# Count custom hooks following naming convention (should be at least 3)
find apps/cli/src/hooks -name 'use-*.ts' -o -name 'use-*.tsx' | wc -l

# Verify hooks usage in screen components
grep -r 'useState\|useEffect\|useCallback' apps/cli/src/components/screens/*.tsx | wc -l
```

**Accept when:**
- All screen components in apps/cli/src/components/screens use functional components with hooks (class component count is 0 or only in documented exceptions)
- Custom hooks directory contains at least 3 reusable hooks following the use-* naming convention
- Screen components demonstrate separation of concerns with business logic in custom hooks and presentation in component files

<enforcement>
Verification is MANDATORY. Claude Code MUST:
- Run automated ESLint checks using eslint-plugin-react-hooks
- Verify hooks usage patterns during code review
- Fail CI pipeline if ESLint hooks rules are violated
- Reject pull requests with class-based screen components unless exception is documented
- Require all violations to be addressed before merge approval

Exception process:
- Developer submits exception request to Tech Lead with justification and migration plan
- Tech Lead reviews request against policy exception criteria (EXC-001, EXC-002)
- Approved exceptions must be documented in code comments with EXCEPTION: prefix and ticket reference
- Exceptions are reviewed quarterly and migration plans are tracked in backlog
</enforcement>
