<rule_activation id="272ddaa1-ede7-447b-b31f-9b5b9932465c" title="Adopt MCP Server Pattern for Service Integration Boundaries: Service Integration Boundaries" applies_to="**/*">
These rules are ALWAYS ACTIVE for all service integration implementations involving MCP (Model Context Protocol) servers, proxy servers, and session management components.

**In scope:**
- All MCP server implementations (live-view-server, mcp-session, etc.)
- Proxy server implementations for replay and debugging functionality
- CLI utility servers that expose functionality to external clients
- Browser package integration servers that bridge web and native contexts
- Session management components that maintain stateful connections

**Out of scope:**
- Internal module-to-module function calls within the same service boundary
- Direct database access patterns (covered by data access ADRs)
- UI component communication patterns (covered by frontend ADRs)
- Build-time code generation and compilation processes

**Exceptions:**
- EX-001: Legacy integrations that predate this ADR and require significant refactoring
- EX-002: Prototype or experimental features in isolated feature branches
</rule_activation>

### Rules

- **R-MCP-001** MUST: Service integration boundaries MUST be implemented using dedicated server classes that encapsulate protocol-specific communication logic.

- **R-MCP-002** MUST: Server classes MUST implement lifecycle methods (start, stop) for operational management.

- **R-MCP-003** SHOULD: Use TypeScript interfaces to define server contracts and ensure type safety across integration boundaries.

- **R-MCP-004** SHOULD: Implement structured logging at server boundaries to enable distributed tracing and debugging of integration issues.

- **R-MCP-005** SHOULD: Consider using a base server class or mixin pattern to share common lifecycle management, error handling, and logging logic.

- **R-MCP-006** SHOULD: Document MCP tool registrations and protocol extensions in a central registry to prevent naming conflicts and enable discovery.

- **R-MCP-007** SHOULD: Implement graceful shutdown handlers that drain in-flight requests and clean up resources before process termination.

- **R-MCP-008** SHOULD: Implement health checks, timeout policies, retry logic with exponential backoff, and circuit breaker patterns at integration boundaries.

- **R-MCP-009** SHOULD: Implement session timeout policies, connection pooling with limits, and automated cleanup of idle sessions.

### Verify

```bash
# Count server class implementations matching MCP/Proxy/Session patterns
grep -r "class.*Server" --include="*.ts" | grep -E "(MCP|Proxy|Session)" | wc -l

# Count server interface implementations
grep -r "implements.*Server" --include="*.ts" | wc -l

# Find server files with lifecycle methods
find . -name "*-server.ts" -o -name "*-session.ts" | xargs grep -l "start\|stop" | wc -l
```

**Accept when:**
- At least 3 server implementation files exist matching the pattern (*-server.ts, *-session.ts)
- Server classes implement lifecycle methods (start, stop) for operational management
- MCP protocol compliance is verified through protocol-specific tests or validation

<enforcement>
Verification is mandatory:
- CI pipeline fails if server implementations lack required lifecycle methods
- Code review blocks merge if integration boundaries bypass server pattern without documented exception
- Quarterly architecture audits identify non-compliant integrations for remediation

**Exception process:**
1. Submit exception request to architecture review board with justification and impact analysis
2. Provide migration plan with timeline if exception is temporary
3. Document approved exceptions in service README and architecture decision log

Claude Code MUST NOT skip or defer verification when working with service integration boundaries.
</enforcement>
